# ADR-0013: Staff access and manual advance payments

**Status:** Draft — Founder Review
**Date:** 2026-11-22
**Deciders:** Founder
**Related:** [ADR-0003](0003-authentication-foundation.md) (roles, `user_access`, audit), [ADR-0005](0005-operation-idempotency.md), [ADR-0011](0011-founder-acceptance-and-customer-sign-in.md) (customer sign-in), [Order policy decisions](../product/order-policy-decisions.md) (section 5), [Requirements](../product/requirements.md) (OF-11, PM-1 to PM-6)

**In short:** The founder's gate instruction of 2026-11-22 authorised staff accounts with limited roles and optional manual advance payments (bKash, Nagad, bank transfer) next to cash on delivery. This records how they are built. The role subsets, the 72-hour link lifetime and the payment details below are engineering choices awaiting the founder's review; no payment gateway, courier or messaging integration is built.

## Staff access

| Area | Decision |
|---|---|
| Roles | `owner` (every permission, unchanged) and four staff roles: `manager`, `orders`, `catalogue`, `inventory`. A role grants nothing by itself: `src/modules/auth/permissions.ts` lists each role's named permissions, and every page, Server Action, `/api/v1` route and operation checks the permission on the server. The role is read from PostgreSQL on every request, so a change applies at once. |
| New permissions | `stock:count` (start a count and enter counted units; applying needs `stock:adjust`), `returns:decide` (approve or reject a return after inspection, which approves its refund), `payments:verify` (confirm, reject or undo a manual advance payment; cancel an order that holds verified advance money). `orders:write` now explicitly covers no money: COD, refunds and advance payments need `payments:record` or `payments:verify`. |
| Role subsets | Manager: catalogue (edit and review, not publish), all stock work, everyday orders, dashboard and reports. Orders Staff: orders and the customer details needed to deliver them; reads products and stock. Catalogue Staff: draft products, photos, categories, size charts, variants, preview; cannot review or publish, sees no orders. Inventory Staff: receive stock and count it; applying a count or adjusting stock waits for a Manager or the Owner. Only the Owner records or verifies money, decides returns, publishes, edits settings and payment methods, exports, manages staff, policies and launch work. |
| Who manages staff | The Owner (`users:manage`), on Admin → Settings → Staff & access. Staff never get the Owner role: invitations carry a staff role only (database check), no operation writes `owner`, and nothing on the page can change, disable or sign out an Owner, so the last Owner can never be locked out from there. |
| Invitations | The Owner enters an email and a role. A one-time link (32 random bytes; only its SHA-256 digest is stored in `staff_invitations`) works once, for 72 hours; a new link for the same address revokes the old one. With email set up (`RESEND_API_KEY`, `EMAIL_FROM`) it is emailed; otherwise, or if sending fails, it is shown once for the Owner to pass on privately. The link carries the token in the URL fragment (`/admin/invite#t=…`), which browsers never send to a server; the page removes it from the address bar and posts it in a Server Action body. The person chooses their own name and password (15 to 128 characters); the account (user, credential, access) is created in one transaction under the same table locks as the Owner set-up. An address that already has an Admin account cannot be invited. Redeeming is rate limited storewide (`staff-invite`, 20 a minute). |
| Lost passwords | Staff have no recovery codes (those recover the Owner). The Owner sends a set-password link (same mechanism, kind `password`); using it replaces the password and ends every session of that account. |
| Disable, re-enable, sign out | Disabling sets `disabled_at`; the existing trigger deletes every session at once and the session-creation hook refuses new ones. "Sign out everywhere" deletes the account's sessions and leaves its password working. |
| Audit | Every Staff & access change writes an `auth_events` row naming the Owner (or, for joining and setting a password, the person): `staff_invited`, `staff_invitation_revoked`, `staff_joined`, `staff_role_changed`, `staff_disabled`, `staff_enabled`, `staff_sessions_revoked`, `staff_password_link`, `staff_password_set`, with ids and roles only (no email address). The `user_access` trigger keeps recording every access change too. Order history shows the acting person's name and role. |
| Customer separation | Unchanged (ADR-0011): customers are a separate Better Auth instance with its own tables, cookies and secret; `user_access` can only reference Admin users. A staff address that is also a customer address is two unrelated accounts. |

## Manual advance payments

| Area | Decision |
|---|---|
| Methods | Cash on delivery is always offered. bKash, Nagad and bank transfer (`payment_methods`, one row each) are offered only after the Owner enters the receiving details and ticks that the account may receive the store's payments (database check: an enabled method has its details and an approval). Wallets need a Bangladesh mobile number and an account type (merchant: customers use Payment; personal: Send Money); banks need a bank name and account number, branch and routing number optional. Nothing is prefilled. No PIN, OTP, card number, banking password or gateway credential exists anywhere. |
| Choosing | At checkout (and for an assisted order in Admin) the customer chooses cash on delivery or an enabled method; `orders.payment_method` records it and the customer cannot change it later. A method disabled between showing and submitting is refused in the order's transaction (`PAYMENT_METHOD_UNAVAILABLE`). |
| Paying | The confirmation and the private tracking page show the store's current receiving details and the amount still due, and say that this is not an online payment. The customer sends money with their own app or bank, then enters the transaction ID on the tracking page (`POST /api/track/payment`, the tracking link is the credential; only the reference is accepted, never a method or amount). At most 3 references wait for the shop at once and 10 per order. |
| Verifying | Only `payments:verify` (the Owner) records money: the amount that actually arrived (partial allowed, never more than still due) and the date. One `advance_received` ledger row, the order's `advance_received_paisa` and its derived payment status change in the same transaction. A unique index lets one reference (method plus ID) count once across all orders. A reference that does not match the account is rejected with a reason; the customer is asked to contact the shop and may send another. A mistaken verification is undone by an `advance_reversed` row (never by editing history), refused once any of that money was refunded. The Owner can also record a transfer the customer sent no ID for. |
| Meaning | A reference proves nothing; the customer sees "awaiting verification" until the Owner verifies. Payment status counts COD collected plus verified advance money against the total. COD can only be collected for what is still due. Advance money is never recorded as courier-collected COD. |
| Stock and timing | Verifying money never confirms an order, reserves stock or revives an expired reservation: rule D is unchanged, and a late payment after expiry is recorded as money while the order still needs the Owner's confirmation (which reserves again only if stock is available). |
| Cancellation and refunds | Cancelling an order that holds verified advance money needs `payments:verify` too. The order then shows "Refund due" (order list, dashboard, reports, tracking page) until the Owner records the refund actually paid by hand (`advance_refunded`, `payments:record`, at most what was received and not refunded). The same applies to a prepaid parcel that comes back undelivered (RTO received): it cannot be closed until the refund is recorded. Nothing is refunded automatically. Return refunds (rule M) may now draw on verified advance money as well as COD. |
| Accounting | `payment_entries` stays append-only with three new kinds; database checks keep received money within the total, refunds within received money, advance money off COD orders, and payment status a function of the amounts. Reports, the reconciliation check and the exports show advance money separately from COD. |
| Gateways later | A gateway would be a new payment method whose verification comes from the provider's signed callback instead of the Owner. The order, ledger and status model above stays; nothing of a gateway (SDK, keys, callback route) exists. |

## Consequences

- Migrations 0024 (staff) and 0025 (payments) are additive: new tables and columns with defaults, and checks dropped and re-created only to widen them. The current code needs both; old code keeps working on the new schema, so the database can be migrated before the new code is deployed.
- `/api/v1` is now usable by any Admin account with the operation's permission (Bearer, unchanged), version 1.7.0.
- Each Staff & access page load runs a few small queries; nothing is cached, so a disabled account loses access on its next request.

## Not decided or not built

Founder decisions are listed in [storefront-launch-decisions.md](../product/storefront-launch-decisions.md) (P1 to P8): the role subsets themselves; Owner-sent set-password links as the staff password recovery (CLAUDE.md lists account recovery as unresolved, so this is built pending confirmation); whether a Manager should see sales and money figures (the dashboard and reports do show them now); whether an order must be paid before dispatch (now a warning, not a rule); how an overpayment, a refund amount or a refund deadline for a cancelled prepaid order is handled; whether personal wallet accounts may be used. Not built: per-person permission overrides, 2FA, staff password change in Admin (Better Auth's change-password endpoint exists; there is no form), staff management over `/api/v1`, payment gateways, automatic matching of statements to references, courier APIs and WhatsApp notifications ([future-integrations.md](../architecture/future-integrations.md)).
