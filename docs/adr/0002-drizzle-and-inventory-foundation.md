# ADR-0002: Drizzle ORM and the catalogue and inventory data foundation

**Status:** Draft — Founder Review
**Date:** 2026-11-14
**Deciders:** Founder
**Related:** [ADR-0001](0001-application-stack.md), [Product requirements](../product/requirements.md) (I-1 to I-4, I-9 to I-11, O-5, O-6, OF-9)

**In short:** The founder approved Drizzle ORM and the data decisions below for implementation in Gate G.3 (2026-11-14). They came from the Gate G.2 design review, where they were proposals. This ADR records what was built. Order reservation, cancellation, returns, RTO, idempotency, authentication and APIs are **not** decided here.

## Context

Requirement EN-2 asks for reviewed, repeatable migrations; EN-3 asks for parameterised queries or a safe ORM. ADR-0001 left the ORM open, with Drizzle proposed and Prisma as the alternative. The first domain work (catalogue and stock) needs both a schema tool and a query layer over the existing `pg` driver.

## Decision (founder-approved for Gate G.3)

| Area | Decision |
|---|---|
| ORM | `drizzle-orm` 0.45.4 over the existing `pg` driver; `drizzle-kit` 0.31.11 for migrations. Exact versions, no prereleases. |
| Migrations | Schema in TypeScript (`src/db/schema.ts`). SQL generated by `drizzle-kit generate`, reviewed, and committed with its metadata in `drizzle/`. Triggers live in reviewed custom SQL migrations. `drizzle-kit push` is not used. |
| Catalogue | Product → Variant. A variant is one sellable SKU with its own price and stock (I-9). |
| SKU | Founder-entered, stored in canonical form and unique in PostgreSQL (I-10): 1–64 ASCII uppercase letters, digits, hyphens and underscores. Input is trimmed and a–z uppercased before validation; spaces, Unicode letters and other symbols are rejected. Gate G.3 first built a looser rule (trimmed, Unicode NFC, uppercase); migration `0002` replaced it in Gate G.3a. The business structure of a SKU is still to be agreed. |
| Money | Integer paisa in PostgreSQL `bigint`, read as a JavaScript `number`. A CHECK requires a price greater than zero and at most 2^53 − 1, so every value is exact as a `number` and serialises to JSON without loss (O-5). Zero-priced variants are invalid. |
| Time | `timestamptz`, set by the database clock (UTC) (O-6). |
| Stock | One `on_hand` balance per SKU (non-negative by CHECK) plus an append-only `stock_movements` ledger (I-2, receipt and adjustment only). |
| Writes | Each stock change runs one transaction: conditional `UPDATE` of the balance (`on_hand + delta >= 0`) with the affected-row count checked, then the ledger insert. Any failure rolls back both. |
| Slugs | Lowercase ASCII letters, digits and single hyphens (product URLs). Names and descriptions keep full Unicode, including Bangla. |
| Inactive SKUs | May receive physical stock. Inactive status does not authorise selling; selling logic does not exist yet. |
| Actors | Ledger rows record `actor_type` and `actor_ref`. Only `system` actors (named machine sources) are allowed until authentication is approved; the database rejects anything else (OF-9). Extended by [ADR-0003](0003-authentication-foundation.md): authenticated `user` actors, migration `0004`. |

## Consequences

- Drizzle adds a thin, typed query builder with no runtime engine or code-generation step. Errors are wrapped in `DrizzleQueryError`, whose message **includes query parameters**; it must never be logged or shown as is.
- Prices as `number` are exact up to 2^53 − 1 paisa. Sums across many orders (future reports) should be computed in PostgreSQL or with `bigint` if they could exceed that.
- The append-only trigger blocks `UPDATE`, `DELETE` and `TRUNCATE` for ordinary SQL, but the table owner or a superuser can drop or disable it. Today the application role owns the tables; a separate migration owner and a runtime role with only `INSERT` and `SELECT` on the ledger would close that gap and belongs with the hosting decision.
- `on_hand = SUM(quantity_delta)` holds because the services are the only write path and both writes share a transaction. The database does not enforce it against arbitrary privileged SQL; an integration test checks it.
- Concurrent decrements of one SKU serialise on its balance row (READ COMMITTED re-checks the condition after the lock wait). This proves stock-operation integrity, not checkout overselling prevention (G-1), which depends on reservation rules O-9 to O-12.

## Not decided

- Idempotency of stock operations. A unique key per ledger row could make a single-SKU receipt retry-safe, but it would fix a design that a multi-SKU operation (an order touching several SKUs) may contradict. Deferred until that operation model is designed (O-3, API-8, G-2). Since resolved at the operation level, not per ledger row: [ADR-0005](0005-operation-idempotency.md).
- Reservation, holds, cancellation, returns, RTO and quarantine stock (O-9 to O-14, I-7).
- Product publication rules (I-6). Products are `draft` or `archived` only, so none is publicly sellable.
- Production migration procedure and database roles (ADR-0001, items 1 and 2). Development migrations run through `npm run db:migrate`, which checks the target before changing anything; those checks prevent mistakes and are not a security boundary (README.md, Database migrations).

## Alternatives considered

Prisma (ADR-0001, item 3): a heavier runtime and schema language; not chosen by the founder.
