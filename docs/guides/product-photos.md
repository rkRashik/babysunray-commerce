# Product photos

**Status:** Draft — Founder Review
**Purpose:** How product photos are uploaded, checked, stored, served and backed up.

Admin panel only, development storage only (`src/modules/media`, [ADR-0006](../adr/0006-product-media-storage.md)). Files live in the folder named by `MEDIA_STORAGE_DIR`: an absolute path to an existing folder **outside** the project (never in Git or `public/`). Without it, photos cannot be uploaded and the admin panel says why. In production the local folder is refused unless `MEDIA_LOCAL_STORAGE_IN_PRODUCTION=allow` (a deployment decision for a host with a persistent, backed-up disk; no such host is chosen).

- **Upload:** JPEG, PNG or WebP decided by the file's bytes (never its name), at most 10 MB and 200 to 8,000 pixels a side, read with a byte limit. `sharp` decodes the whole image, so damaged, truncated, animated or fake files are refused; it is re-encoded in the same format at most 2,400 pixels a side with orientation applied and all metadata removed (EXIF including GPS, XMP, comments). Only that copy is stored, under a random key. SVG, HTML and anything else are refused.
- **Management:** English and Bangla descriptions (alt text), order (first is shown in lists), replace in place, remove (needs a tick and a confirmation; the stored file is deleted). Every change names the product version, so a second tab is refused, and runs once per idempotency key. At most 12 photos per product (a technical bound).
- **Consistency:** a new file is written before its record and deleted again if the record is not committed (refused, failed or a replay); a replaced or removed file is deleted after its record. `product_media` is the manifest (product, key, type, size, SHA-256, times). `npm run media:verify` lists missing, changed, unreferenced and unexpected files; the Exports page has the manifest as a dataset. Admin → Photo storage shows the same check and can delete files without a record after an explicit tick (only if untouched for an hour).
- **Serving:** `/office/media/{id}` for a signed-in admin only (`401` otherwise), `private, no-cache` with an ETag, `nosniff` and a sandbox policy; `?w=320|640|1280` gives a smaller copy. Resized copies are cached in memory (32 MB); at most two image decodes or resizes run at once.
- **Backups:** database backups hold the photo records, not the files. `npm run media:backup` makes an encrypted photo backup with the same construction as the database backup, accepted only if folder and records are consistent; `media:backup:verify`, `media:restore` (into an empty folder), `recovery:check` and the fictional `media:drill` complete it ([runbook](../operations/runbook.md), section 7a).
